Architecture

How an inbound event becomes a durable, branching conversation.

Data flow

Customer system ──POST /api/v1/ingest/:id (HMAC)──▶ FastAPI
       │
       ▼ buffer
   RabbitMQ ──normalize + match──▶ Worker ──start──▶ Temporal
                                     │                  │
                                     │   activities: render + send + log
                                     ▼                  ▼
                                  Postgres         Email / Slack / Teams
                                                        │
   Technician ──click action link──▶ FastAPI ──signal──▶ Temporal
                                     │
                                     ▼ run.resolved / run.escalated
                              Outbound webhook (signed, retried)

Components

API (FastAPI)

Ingest, auth + RBAC, tracking links, dashboard data, admin/platform config, SSO. Stateless behind TLS.

Worker

Runs the Temporal worker plus two RabbitMQ consumers (ingest normalize/match, outbound webhook delivery with retries).

Temporal

One SequenceRunWorkflow per run. Durable timers + signals; all I/O lives in activities.

RabbitMQ

Ingest buffering and outbound retries via a dead-letter exchange (3 attempts, then give up).

The workflow

Each run is exactly one execution of SequenceRunWorkflow (backend/src/dripstack/worker/workflows.py). It is deterministic and performs no I/O directly — every side effect (DB, rendering, send, webhooks) is an activity. For each step the workflow:

  1. records the current step,
  2. workflow.sleep(delay) — a durable timer that survives restarts,
  3. runs render_and_send_step (render for the channel + deliver + write a MessageLog),
  4. if the step has waitForAction, it wait_condition(...) racing a signal against a durable timeout:
    • a resolve signal → finalize resolved (records time-to-resolution),
    • an escalate signal or a next_step timeout → continue,
    • an end timeout → finalize escalated + publish outbound webhooks.

Signals are buffered one-per-wait, so a click landing while earlier activities run is queued (not lost) and one click never satisfies two waits. Covered by a time-skipping test (backend/tests/test_workflow.py) that fast-forwards the timeout.

Rendering

Emails are server-rendered with Jinja2 + Pygments (Outlook table-wrapped code, a 90 KB Gmail-clip guard, AI explanation or fallback, collapsible logs). Interpolation uses a custom {{ $.path }} syntax kept separate from Jinja's delimiters. Slack uses Block Kit; Teams uses an Adaptive/MessageCard payload.
