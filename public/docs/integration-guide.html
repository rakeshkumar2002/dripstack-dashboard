Orientation

Turn a machine error into something a technician can act on

DripStack takes a raw error from your product, explains it in plain English, emails the person standing in front of the equipment, and runs a branching follow-up until they resolve it or it escalates.

It detects nothing. Your application decides what is worth escalating and pushes it here. That distinction matters: DripStack is not a logging or observability tool, and it does not replace Sentry, CloudWatch or your alerting. It sits downstream of all of them and handles the part none of them do — telling a non-engineer what to physically go and do.

Who receives

A field technician, contractor or site manager — someone who cannot read a stack trace.

Who integrates

The equipment or software vendor whose support desk currently absorbs the call.

What it costs them

Two HTTP endpoints. Roughly twenty lines either side.

Build · one of two

Send an event

Sign the request body with your event source's secret and post it. You get 202 back — accepted and queued — so never block your request path waiting on it.

// Sign the EXACT bytes you send — serialise once, hash that string, post that string.
const body = JSON.stringify(payload);
const sig  = crypto.createHmac('sha256', SIGNING_SECRET).update(body, 'utf8').digest('hex');

await fetch(`${DRIPSTACK_URL}/api/v1/ingest/${EVENT_SOURCE_ID}`, {
  method: 'POST',
  headers: {
    'content-type': 'application/json',
    'x-dripstack-signature': `sha256=${sig}`,
  },
  body,
});
# Sign the EXACT bytes you send — dumps once, hash that string, post that string.
body = json.dumps(payload)
sig  = hmac.new(SIGNING_SECRET.encode(), body.encode(), hashlib.sha256).hexdigest()

httpx.post(
    f"{DRIPSTACK_URL}/api/v1/ingest/{EVENT_SOURCE_ID}",
    headers={
        "content-type": "application/json",
        "x-dripstack-signature": f"sha256={sig}",
    },
    content=body,
)
BODY='{"eventType":"equipment.fault","technician":{"email":"tech@acme.com"}}'
SIG=$(printf '%s' "$BODY" | openssl dgst -sha256 -hmac "$SIGNING_SECRET" | sed 's/^.* //')

curl -X POST "$DRIPSTACK_URL/api/v1/ingest/$EVENT_SOURCE_ID" \
  -H 'content-type: application/json' \
  -H "x-dripstack-signature: sha256=$SIG" \
  --data-binary "$BODY"

The payload is yours, with two conventions

FieldWhy it matters
eventTypeWhat sequence trigger rules match on.
technician.emailWho gets contacted. contactEmail, contact.email and user.email also work. The contact is created automatically the first time.

Everything else is your own shape — sequences pull from it by JSONPath. Send the error code, the device, the site and the raw log, because the explanation can only be as good as what you hand over. {"error":"request failed"} produces a useless email.

Where do I get the ID and secret? Dashboard → Settings → Event sources. The same page holds your API keys.
Build · two of two

Receive callbacks

So your product learns how the conversation ended without anyone logging into DripStack. Return any 2xx once you have durably accepted it; anything else is retried with backoff through a dead-letter queue.

express 
// express.raw, NOT express.json — the signature covers the bytes on the wire.
app.post('/webhooks/dripstack', express.raw({ type: '*/*' }), (req, res) => {
  const raw = req.body.toString('utf8');
  const expected = crypto.createHmac('sha256', WEBHOOK_SECRET).update(raw, 'utf8').digest('hex');
  if (!signatureMatches(expected, req.get('x-dripstack-signature'))) return res.sendStatus(401);

  const { event, data } = JSON.parse(raw);   // run.resolved | run.escalated
  // …close the work order, page an engineer, whatever your product does
  res.json({ ok: true });
});
register it once 
curl -X POST "$DRIPSTACK_URL/api/v1/outbound-webhooks" \
  -H "authorization: Bearer $TOKEN" -H 'content-type: application/json' \
  -d '{"url":"https://your-app/webhooks/dripstack","events":["run.resolved","run.escalated"]}'

# The response contains the signing secret. It is shown once.

Five traps worth knowing before you start

Parse the body, don't re-serialise it

The signature covers the bytes on the wire. express.json() parses and discards them, and re-stringifying gives different bytes — key order and whitespace differ — so every check fails. The same rule applies outbound.

There are two different secrets

The ingest secret belongs to the event source. The callback secret belongs to the webhook registration. Swapping them gives a 401 that looks exactly like a wrong value.

Deduplication keys on sequence + contact

Not on whatever your app considers the failing thing. Two devices failing for the same technician produce one run, and the worker logs active run exists — skipping new run. There is also a separate five-minute payload-hash dedupe for byte-identical retries. Key your local state on what you sent, not on an assumed one-run-per-event.

The callback URL must be reachable from DripStack

Not just from your laptop. A localhost address, a private network, or anything behind a firewall will never receive a callback — use a publicly resolvable URL, or a tunnel while developing.

Opening an action link does not trigger the action

A tracked link opens a confirmation page; only the POST behind its button resolves or escalates. That is deliberate — it stops mail scanners and browser prefetch from silently closing incidents — but it surprises anyone testing the flow with curl.

Every tracked link is bound to its run. An altered token, a missing token, or a log token reused for a different block are all refused with 403.

Reference

Known limits

  • Resolve and escalate are not symmetric. Resolve closes the run immediately. "I need help" only advances the drip — the run is marked escalated when the steps run out, so your callback fires minutes later rather than on the click.
  • Send failures are not retried. A momentary provider outage is recorded the same way as a permanently bad address, and the sequence continues without that message.
  • Dedupe has no fingerprinting. Ten variations of one failure produce ten runs unless they share a contact and sequence.
  • Explanations degrade, they do not block. No key, a rate-limited model or a malformed reply all fall back to written guidance, and the email still sends.
  • No log search, no on-call rotas, no maintenance windows. Deliberate — those belong to the tools this sits downstream of.
