Integrations

Every external integration is production-ready and degrades gracefully when unconfigured, so the demo runs keyless.

Email

The provider is chosen per organization (Email settings page) and falls back to the env EMAIL_PROVIDER.

ProviderBehaviourSetup
logRenders to /dev/emails; sends nothing. Keyless default.—
resendReal delivery via the Resend HTTPS API.EMAIL_PROVIDER=resend + RESEND_API_KEY. Verify your sending domain in Resend.
sesReal delivery via AWS SESv2 (aioboto3).uv sync --extra ses, EMAIL_PROVIDER=ses, AWS_REGION; credentials from the boto3 chain / IAM role. Optional SES_CONFIGURATION_SET.

Slack & Teams

Delivered natively via per-org incoming webhook URLs stored in the ChannelIntegration table (never in Organization.settings, which is serialized to clients). Slack receives a Block Kit message; Teams receives an Adaptive MessageCard. When a channel isn't configured, a stub sender logs instead.

PUT /api/v1/channels/slack
{ "webhookUrl": "https://hooks.slack.com/services/T.../B.../xxxx", "enabled": true }

POST /api/v1/channels/slack/test     # post a test message
The API only ever returns a masked target (https://hooks.slack.com/…xxxx); the raw URL is never sent back to clients.

Outbound webhooks

Subscribe external systems to run-lifecycle events (run.resolved, run.escalated, run.completed, run.failed). Each delivery is signed with x-dripstack-signature (HMAC over the raw body) and retried via a dead-letter exchange (3 attempts).

POST /api/v1/outbound-webhooks
{ "url": "https://example.com/hooks/dripstack", "events": ["run.resolved","run.escalated"] }

Single sign-on (OIDC)

DripStack supports the OpenID Connect authorization-code flow, configured per organization. Works with Google, Okta, Microsoft Entra ID, Auth0, and any compliant OIDC provider.

1 · Configure (admin)

PUT /api/v1/sso
{
  "issuer": "https://accounts.google.com",
  "clientId": "xxxx.apps.googleusercontent.com",
  "clientSecret": "••••••",          // write-only; omit on update to keep it
  "enabled": true,
  "autoProvision": false,             // create users on first login?
  "allowedDomain": "acme.com",        // optional email-domain allow-list
  "defaultRoleSlug": "customer-member"
}

In your IdP, register the redirect URI {APP_BASE_URL}/api/v1/auth/sso/callback. GET /api/v1/sso returns a masked view — the client secret is never returned.

2 · Sign in

From the dashboard login screen, choose Single sign-on (OIDC), enter the organization ID, and continue. Under the hood:

  1. GET /api/v1/auth/sso/{org}/start → redirects to the IdP with a signed, short-lived state token.
  2. The IdP redirects back to /api/v1/auth/sso/callback; DripStack exchanges the code, fetches userinfo, verifies the email, and matches (or provisions) the org user.
  3. DripStack issues its own access + refresh tokens and hands them to the dashboard's /sso/callback page via the URL fragment.
Sign-in is denied (403) when the email isn't verified, the domain isn't allowed, the user doesn't exist and auto-provision is off, or the account is disabled. Every SSO login is recorded in the audit log.

AI explanations

Set AI_PROVIDER=anthropic + ANTHROPIC_API_KEY for real plain-language error explanations (model claude-sonnet-4-6). The default fallback provider produces a deterministic, schema-validated explanation with no key.
